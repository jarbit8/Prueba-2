Key Features

Everything a personal finance platform needs, built with enterprise-grade architecture.

👤

Person Management

Each person has a name, address, birthdate, birthplace, family relations (mother, father, siblings) and a personal ledger.

👨‍👩‍👧‍👦

Groups & Families

People can form groups (e.g. families). Each group has administrators, a description, a creation date and a shared ledger.

💰

Financial Transactions

Register credit/debit transactions in a Ledger with description, value, date and category. Supports scheduling with periodicity.

🏦

Accounts & Categories

Create personal and group accounts. Organize transactions by custom categories per person or group.

📊

Transaction Search

Search account records within a given period. Get a filtered view of group or personal transactions by date range.

🔐

Role-Based Access

Group administrators can manage members, categories and accounts. Regular members have read/write access to shared ledgers.

DDD Architecture

Four conceptual layers — each with a single, well-defined responsibility.

1

User Interface (React)

Presents information to the user and interprets commands. Communicates via REST with the Controller layer.

2

Controller Layer (Spring REST)

REST controllers receive HTTP requests, create DTOs via Assemblers and delegate to Application Services.

3

Application Layer

Thin services that orchestrate domain logic without containing business rules. One service per use case.

4

Domain Layer (DDD Core)

Entities, Value Objects, Aggregates and domain services. This is the heart of the business model.

5

Infrastructure / Persistence (H2 + JPA)

One repository per aggregate root. Data Models and Assemblers handle the mapping from domain to persistence.

Design Principles

The project applies industry-standard patterns to achieve high cohesion and low coupling.

GRASP

High Cohesion

Each class has a single, well-focused responsibility.

GRASP

Low Coupling

Modules depend on abstractions, not concrete implementations.

SOLID

Single Responsibility

One reason to change per class — from controllers to repositories.

SOLID

Open / Closed

Extend behavior via interfaces without modifying existing code.

SOLID

Dependency Inversion

Services depend on repository interfaces, not on concrete JPA classes.

GoF

Factory / Assembler

DTO Assemblers encapsulate object construction from primitive types.

DDD

Aggregate Root

Person and Group are aggregate roots with their own repository each.

DDD

Value Objects

Immutable types like PersonID, AccountID and CategoryID with no identity of their own.
